# PB-001 — Brute-Force Authentication Response Playbook

## 1. Purpose

This playbook defines a repeatable SOC workflow for investigating and responding to suspected brute-force authentication activity.

It is designed for use with the CYBERNOVA SOC Operations Laboratory and provides a structured process for:

* alert validation;
* triage;
* evidence preservation;
* authentication investigation;
* threat-intelligence assessment;
* containment decision-making;
* eradication and recovery planning;
* detection improvement; and
* incident closure.

This playbook is an operational laboratory procedure.

It does not represent production incident-response activity or professional SOC employment experience.

---

## 2. Trigger

Use this playbook when a brute-force authentication alert is generated.

Primary detection:

```text
DET-AUTH-001
SSH Brute-Force Authentication Detection
```

Typical trigger characteristics include:

* repeated authentication failures;
* repeated failures from the same source;
* activity exceeding the configured threshold;
* authentication activity occurring within the configured detection window;
* and, where available, a subsequent successful authentication.

The presence of an alert does not independently prove compromise.

---

## 3. Severity Guidance

Default severity:

```text
High
```

Escalate investigative priority when additional evidence is present, including:

* successful authentication following repeated failures;
* privileged account involvement;
* suspicious post-authentication commands;
* persistence activity;
* suspicious network activity;
* malware execution;
* multiple related detections;
* evidence of credential abuse;
* or a correlated multi-stage sequence.

A correlated multi-stage sequence may result in:

```text
Critical
```

depending on the correlation logic and available evidence.

Severity should remain evidence-driven.

---

## 4. Initial Alert Validation

The analyst should first confirm that the alert is structurally valid.

Verify:

* alert ID;
* detection ID;
* detection version;
* timestamp;
* first-seen timestamp;
* last-seen timestamp;
* host;
* source IP;
* username;
* failed-attempt count;
* configured threshold;
* detection window;
* supporting event IDs;
* successful-authentication status, if available;
* severity;
* confidence.

### Validation Questions

1. Is the alert generated by the expected detection?
2. Is the timestamp valid and timezone-aware?
3. Are the host, user, and source IP populated?
4. Does the observed failure count exceed the configured threshold?
5. Are the supporting events available?
6. Is there evidence of a successful authentication?
7. Are there related alerts from the same host, user, or source?

If the alert fails structural validation, preserve the alert as evidence and escalate the detection-quality issue rather than assuming malicious activity.

---

## 5. Triage

Determine whether the observed activity is:

```text
Likely benign
      ↓
Suspicious
      ↓
High-priority investigation
```

### Review

Examine:

* source IP;
* target host;
* targeted username;
* authentication protocol;
* number of failures;
* time distribution;
* successful authentication;
* account privilege level;
* related authentication activity;
* related endpoint activity;
* related network activity;
* persistence activity.

### Important Distinction

Repeated authentication failures alone do not establish:

* attacker identity;
* unauthorized access;
* credential compromise;
* successful compromise; or
* persistence.

These require additional evidence.

---

## 6. Evidence Preservation

Preserve the original evidence before modifying or filtering it.

Preserve:

* original telemetry;
* normalized alert;
* detection output;
* supporting event IDs;
* timestamps;
* source IP;
* target host;
* username;
* authentication protocol;
* related alerts;
* relevant configuration;
* investigation notes.

Record the relationship:

```text
Telemetry Event
      ↓
DET-AUTH-001
      ↓
Alert
      ↓
Investigation
```

Do not overwrite original evidence during investigation.

---

## 7. Authentication Investigation

Reconstruct the authentication sequence.

Determine:

* when failures began;
* how many failures occurred;
* whether failures were consecutive;
* whether attempts targeted one account or multiple accounts;
* whether a successful authentication followed;
* which source generated the activity;
* which host was targeted;
* which account was targeted;
* whether the account was privileged.

### Example Sequence

```text
Failure
Failure
Failure
Failure
Failure
Failure
   ↓
Successful Authentication
   ↓
Session Created
```

A successful authentication after repeated failures increases investigative priority but still does not independently establish unauthorized access.

---

## 8. Source-IP Investigation

Use the source IP as an investigation pivot.

Search the available telemetry for:

* earlier authentication attempts;
* later authentication attempts;
* activity against other hosts;
* activity against other accounts;
* successful authentications;
* network connections;
* endpoint activity;
* persistence indicators.

Determine whether the same source appears elsewhere in the available laboratory telemetry.

### Laboratory Boundary

Synthetic documentation-network addresses must not be treated as evidence of real-world malicious infrastructure.

Do not claim:

* ownership;
* geographic attribution;
* reputation;
* threat-actor attribution;
* or real-world maliciousness

without appropriate external evidence.

---

## 9. Account Investigation

Investigate the targeted account.

Determine:

* account name;
* privilege level;
* expected administrative role;
* authentication history;
* successful sessions;
* session duration;
* commands executed after authentication;
* account-management activity;
* privilege escalation activity.

Pay particular attention to privileged accounts.

For example:

```text
root
administrator
domain administrator
service accounts
```

Privileged-account involvement should increase investigative priority.

---

## 10. Post-Authentication Investigation

If authentication succeeds after repeated failures, pivot into post-authentication telemetry.

Review:

* session creation;
* shell activity;
* executed commands;
* privilege-related commands;
* account enumeration;
* host enumeration;
* network enumeration;
* persistence attempts;
* file modifications;
* suspicious downloads;
* suspicious process execution.

Related detection:

```text
DET-AUTH-003
Suspicious Post-Authentication Privileged Session
```

A sequence such as:

```text
Brute-force activity
      ↓
Successful authentication
      ↓
Privileged session
      ↓
Enumeration
```

should receive higher investigative priority than isolated failed authentication attempts.

---

## 11. Related Detection Investigation

Search for related detections using:

### Host

```text
host
```

### User

```text
user
```

### Source IP

```text
source_ip
```

### Session

```text
session_id
```

### Time

Use the detection window plus an investigation buffer before and after the alert.

Look for:

* endpoint detections;
* malware detections;
* network detections;
* web detections;
* Linux persistence detections;
* file-integrity alerts;
* other authentication alerts.

If several independent detections form a coherent sequence, consider escalation to a multi-stage investigation.

---

## 12. Threat Intelligence Assessment

Assess available intelligence relevant to the observed indicators.

Potential pivots include:

* source IP;
* destination host;
* username;
* domain;
* URL;
* file hash;
* process;
* command line.

Record intelligence confidence separately from detection confidence.

### Do Not Overclaim

Without validated external intelligence, do not state that an IP is:

* malicious;
* associated with a threat actor;
* part of a botnet;
* geographically located in a particular region;
* or owned by a specific organization.

Document intelligence gaps explicitly.

---

## 13. MITRE ATT&CK Context

Brute-force authentication activity may map to:

```text
T1110 — Brute Force
```

Where the telemetry supports a more specific classification, use the appropriate sub-technique.

For SSH authentication activity, the laboratory detection may use:

```text
T1110.001 — Password Guessing
```

Additional techniques should only be mapped when supported by observed evidence.

ATT&CK mapping is contextual and does not independently establish maliciousness.

---

## 14. Containment Decision

Containment should be evidence-driven.

Potential production actions may include:

* blocking a source;
* disabling or locking an account;
* forcing credential rotation;
* terminating suspicious sessions;
* isolating an affected host;
* restricting network access.

These are **response options**, not claims that they were performed.

### Decision Factors

Consider:

* confidence;
* successful authentication;
* account privilege;
* evidence of unauthorized activity;
* additional detections;
* persistence;
* malware;
* business impact;
* operational risk;
* availability requirements.

In the laboratory, containment actions should remain simulated or documented unless an explicitly authorized test environment is being used.

---

## 15. Eradication

If compromise is established through sufficient evidence, eradication planning may include:

* credential rotation;
* removal of unauthorized accounts;
* removal of persistence;
* termination of malicious processes;
* removal of malicious files;
* remediation of exploited configuration;
* patching vulnerable services.

Do not perform destructive actions against systems outside the authorized laboratory environment.

---

## 16. Recovery

Recovery planning should include:

1. restore affected services;
2. validate authentication configuration;
3. verify account integrity;
4. verify persistence mechanisms;
5. validate endpoint state;
6. review subsequent authentication activity;
7. monitor for recurrence.

Recovery should be evidence-based and documented.

---

## 17. Detection Validation

After investigation, evaluate whether the detection behaved correctly.

Review:

* threshold accuracy;
* detection window;
* duplicate handling;
* alert uniqueness;
* timestamp handling;
* false positives;
* false negatives;
* successful-authentication correlation;
* source-IP handling;
* user handling.

For `DET-AUTH-001`, validate that:

```text
failure count >= configured threshold
```

within the configured window produces the expected alert.

Also validate that legitimate activity below the threshold does not generate an alert.

---

## 18. Detection Improvement Feedback

Investigation findings should feed back into detection engineering.

Example:

```text
Investigation
      ↓
Detection weakness identified
      ↓
Detection improvement
      ↓
Regression test
      ↓
Validation
      ↓
Updated detection
```

Potential improvements include:

* better timestamp normalization;
* improved duplicate handling;
* configurable thresholds;
* improved account context;
* successful-authentication correlation;
* source-IP rotation handling;
* distributed attack detection;
* improved alert traceability.

Every improvement should preserve regression coverage.

---

## 19. False-Positive Review

Potential legitimate causes include:

* user password mistakes;
* expired credentials;
* administrative testing;
* automated authentication jobs;
* monitoring systems;
* vulnerability scanners;
* configuration errors.

Investigate contextual evidence before assigning malicious intent.

Document why activity was classified as:

```text
Benign
Suspicious
Confirmed malicious
```

Only use the strongest classification supported by evidence.

---

## 20. Escalation Criteria

Escalate when one or more of the following are present:

* successful authentication after repeated failures;
* privileged account involvement;
* suspicious post-authentication activity;
* persistence;
* malware execution;
* suspicious network activity;
* multiple hosts affected;
* multiple accounts targeted;
* evidence of credential compromise;
* correlated multi-stage detections;
* inability to explain the activity through legitimate administrative behavior.

For a multi-stage sequence involving authentication, post-authentication activity, and persistence, consider the CASE-010 correlation workflow.

---

## 21. Closure Criteria

The investigation may be closed when:

* alert validity has been established;
* supporting evidence has been preserved;
* relevant pivots have been investigated;
* related detections have been reviewed;
* threat-intelligence limitations are documented;
* severity has been justified;
* response decisions are recorded;
* detection weaknesses have been assessed;
* required follow-up actions are documented;
* final analyst assessment is complete.

Closure must not imply compromise unless compromise was actually established.

## 25. Analyst Conclusion

A brute-force authentication alert should be treated as an investigation starting point rather than automatic proof of compromise.

The strongest investigations connect authentication evidence with:

```text
Source
+
Account
+
Host
+
Time
+
Successful Authentication
+
Post-Authentication Activity
+
Related Detections
```

The goal is not simply to block suspicious activity.

The goal is to establish an evidence-driven understanding of what occurred, preserve traceability, challenge alternative explanations, make proportionate response decisions, and improve detection capability through measurable engineering feedback.
