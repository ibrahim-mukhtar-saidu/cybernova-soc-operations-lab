**Playbook ID:** PB-009
**Primary Detection:** `DET-HOST-001` — File Integrity Violation Detection
**Detection Version:** `1.0`
**Related Flagship Case:** CASE-007 — File Integrity Violation
**Environment:** CYBERNOVA SOC Operations Laboratory
**Classification:** Defensive / Laboratory Use
**Status:** Implementation Candidate

---

# 1. Purpose

PB-009 provides a standardized Security Operations Center investigation and response workflow for suspicious file integrity violations detected by `DET-HOST-001`.

The playbook is designed to guide analysts from initial alert validation through evidence preservation, file analysis, host correlation, authentication review, process investigation, threat-intelligence assessment, ATT&CK contextualization, containment, recovery, detection improvement, and case closure.

The playbook emphasizes the distinction between:

* observed telemetry;
* detection-engine output;
* analyst interpretation;
* investigative hypotheses;
* confirmed findings.

A file integrity violation indicates that a file changed.

A file change alone does not establish malicious intent, compromise, persistence, privilege escalation, or unauthorized access.

---

# 2. Scope

This playbook applies to alerts generated by:

`DET-HOST-001`

The current detector identifies clustered file-integrity events when:

* `event_type` is `file_integrity`;
* `status` is `changed`;
* `change_type` is one of:

  * `modified`;
  * `created`;
  * `deleted`;
* events belong to the same host;
* at least two qualifying violations occur;
* the violations fall within the configured five-minute detection window.

The current implementation groups file-integrity events by host.

The detector does not currently establish:

* malicious process attribution;
* malicious command execution;
* successful compromise;
* attacker identity;
* threat actor attribution;
* malware family;
* persistence success;
* unauthorized access by itself.

---

# 5. Detection Logic Summary

The detector:

1. Filters file-integrity events.
2. Requires status `changed`.
3. Accepts `modified`, `created`, and `deleted`.
4. Groups qualifying events by host.
5. Sorts events chronologically.
6. Creates a five-minute window beginning at each candidate event.
7. Counts qualifying violations within that window.
8. Requires at least two violations.
9. Collects affected file paths.
10. Collects change types.
11. Preserves supporting event IDs.
12. Generates a high-severity, high-confidence laboratory alert.

The alert is evidence of clustered file-state changes.

It is not proof that the changes were malicious.

# 48. False-Negative Considerations

The current detector may miss:

* a single malicious file modification;
* modifications separated by more than five minutes;
* activity distributed across hosts;
* changes without valid telemetry;
* telemetry collection failures;
* tampered or deleted evidence;

---

# 49. Adversarial Evasion — Slow Activity

An adversary could modify one file and wait longer than five minutes before modifying another.

This can evade the current clustering threshold.

Improvement opportunities:

* longer analytical windows;
* configurable thresholds;
* baseline-aware correlation;
* historical file-change correlation.

Any improvement must be validated with regression tests.

---

# 50. Adversarial Evasion — Distributed Activity

An adversary could modify different files on different hosts.

Because the current detector groups by host, the events may not form one alert.

Potential improvement:

* cross-host correlation;
* identity-based correlation;
* campaign-level correlation.

# 81. Limitations

The current `DET-HOST-001` implementation has important limitations.

It may not detect:

* isolated file changes;
* slow changes outside five minutes;
* distributed changes across hosts;
* modifications without telemetry;
* evidence deleted before collection;
* activity on unmonitored paths.

The alert ID is currently static for the CASE-007 workflow:

```text
ALERT-CASE-007-DET-HOST-001
```

This should be considered an engineering limitation if the same detection is later reused across multiple independent cases.

Future refactoring should provide deterministic but case-independent alert identity.
