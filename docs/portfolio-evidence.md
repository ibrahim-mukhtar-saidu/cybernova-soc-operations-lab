# CYBERNOVA SOC Operations Lab — Portfolio Evidence

## Document Purpose

This document defines how the **CYBERNOVA SOC Operations Lab** converts
technical work into verifiable portfolio evidence.

The objective is to demonstrate practical cybersecurity capability through
reproducible laboratory activities, documented investigations, tested
detections, security validation, and clear technical reporting.

The portfolio is designed for technical reviewers, cybersecurity recruiters,
SOC hiring managers, security engineers, and other professional reviewers.

The evidence presented by this project represents controlled laboratory work.
It must not be interpreted as production SOC employment or production
enterprise incident-response experience.

---

## 1. Portfolio Evidence Objectives

The portfolio evidence framework is designed to demonstrate the ability to:

- Generate or collect controlled security telemetry.
- Build and test security detections.
- Validate alerts.
- Perform SOC triage.
- Preserve and analyze evidence.
- Construct incident timelines.
- Extract and investigate indicators.
- Perform threat-intelligence enrichment.
- Develop and test hunting hypotheses.
- Map observed behavior to MITRE ATT&CK.
- Recommend or simulate incident-response actions.
- Produce professional investigation reports.
- Measure detection quality.
- Identify security gaps.
- Improve detections based on investigation findings.
- Validate changes through testing.
- Document limitations honestly.
- Reproduce important investigation steps.

4. Evidence Integrity Principles

All portfolio evidence should follow these principles:

Preserve original evidence where practical.
Avoid modifying raw telemetry unnecessarily.
Record transformations.
Record timestamps consistently.
Hash important artifacts where appropriate.
Separate raw evidence from derived analysis.
Distinguish facts from interpretation.
Record uncertainty.
Document limitations.
Never fabricate evidence.

Evidence integrity is more important than making an investigation appear
successful.

5. Evidence Classification

Every important investigative statement should fall into one of the following
categories.

Observed Evidence

A fact directly supported by telemetry or another artifact.

Example:

Observed:
The authentication dataset contains 17 failed login events for account
analyst01 within the defined five-minute window.
Analyst Interpretation

A reasoned interpretation of observed evidence.

Example:

Interpretation:
The event pattern is consistent with a concentrated authentication attack.
Hypothesis

A proposed explanation that requires additional validation.

Example:

Hypothesis:
The successful login following the failed attempts may indicate credential
compromise.
Confirmed Finding

A conclusion supported by sufficient available evidence.

Example:

Finding:
The laboratory scenario confirms that the detection identified the simulated
authentication attack.
Recommended Action

A proposed response or improvement.

Example:

Recommendation:
Investigate the source activity and apply appropriate account protection
controls.
Limitation

A condition that prevents a stronger conclusion.

Example:

Limitation:
The laboratory does not contain endpoint telemetry for the affected identity,
so post-authentication activity cannot be independently confirmed.
6. Evidence Quality Levels

Evidence may be categorized by quality.

Level	Description
E1	Directly observed laboratory evidence
E2	Correlated evidence from multiple laboratory sources
E3	Derived analytical evidence
E4	External contextual evidence
E5	Hypothesis or unvalidated interpretation

Higher levels do not automatically mean more trustworthy evidence.

The classification describes evidence origin and analytical status.

18. Positive Test Evidence

A positive test demonstrates that malicious or suspicious simulated activity
produces the expected detection.

Example:

Scenario:
Five failed authentication attempts from one source within five minutes.

Expected:
Authentication brute-force alert.

Actual:
Alert generated successfully.

Result:
PASS
19. Negative Test Evidence

A negative test demonstrates that normal activity does not unnecessarily
trigger the detection.

Example:

Scenario:
Two normal authentication failures followed by a successful login.

Expected:
No brute-force alert.

Actual:
No alert generated.

Result:
PASS

Negative testing is essential for evaluating false-positive behavior.

45. Evidence Maturity Model

The portfolio evidence can mature through the following stages.

Level 1 — Artifact

The project contains code or documentation.

Level 2 — Demonstration

The artifact produces a working result.

Level 3 — Validation

The result is tested and documented.

Level 4 — Investigation

The result is connected to an investigation workflow.

Level 5 — Operational Lifecycle

The investigation feeds response, reporting, detection improvement, and
security validation.

The objective of the CYBERNOVA SOC Operations Lab is to reach Level 5 for
the flagship cases.
